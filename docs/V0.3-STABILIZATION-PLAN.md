# v0.3 稳定化与正式交付计划

状态：实施进行中。2026-10-19 规划基线：00295d77ab8660565e0772985a4387f9351ffb37。初次规划记录保留，最新实施进度以第5节状态及文末追加记录为准。

本计划是新增阶段，保留既有计划、顺序和历史结果。任务身份仍由使用项目决定，框架不规定固定的研究者、程序员或协调者类型。

## 1. 本阶段目标和完成标准

把已有跨电脑、跨 harness 的准确会话通信整理成可安装、可诊断、可恢复、可查看的稳定版本。本阶段冻结功能范围，重点完成使用和运维闭环。

v0.3 的完成标准：

1. 新机器安装一个固定版本的包，程序、通信 state、缓存与原生聊天分离；按一份入口说明完成接入。
2. 操作者能够核对准确服务、完整 session、工作目录、节点、binding 和 room，并了解该 adapter 的实际收件能力。
3. 暂停后不再开始该 binding 的新投递；恢复保留原绑定和已处理进度，且只有一个所属 worker。
4. 常见中断能按原消息和原生输入证据对账；无法证明结果时保持待核对并给出具体操作指引，不盲目再发。
5. 两台物理机器、两种 harness 围绕一项真实项目任务完成交付、复核和一次修订；消息、原生工具结果及产物均可查。
6. 用户能在查看器中核对全过程；关闭或重启查看器不改变通信行为。
7. 候选包经过干净安装、升级和允许范围内的回退检查；最终发布资产与已验收包字节一致，使用说明对应同一版本。

任意聊天自动接管、所有 harness 全覆盖、所有桌面空闲唤醒、无法证明的 unknown 自动恢复，不属于本版完成门槛。

## 4. 先明确的恢复合同

以下是待实现/收敛的行为要求，不是已存在的新命令。涉及状态修改的具体设计单独保存，完成审查后先写失败用例，再实现。

### 4.1 统一预检

复用 doctor、bindings、node status、sessions 和既有能力合同，按以下顺序给出结果：环境 → 所选原生服务 → 准确聊天与 binding → room/peer → worker → 待核对事项。

每项输出稳定状态码、证据来源、是否实际探测以及具体下一步。默认只读本地已有信息，不创建 node、绑定、room 或模型 turn；native/SSH 深查由操作者显式选择。Kimi 查询可能加载冷会话，必须说明并保留其服务所有权限制。不能将未探测写成在线，也不能把工具存在写成聊天已接入。

优先用已有命令与一份统一配置/报告达到目标。若确需新命令，再决定名称；本文不把新的 inspect/onboard 命令当成已经可用。

### 4.2 保留绑定的暂停与恢复

- 暂停针对完整 binding 身份，保留 node、binding ID/revision、room、session、cursor 和回执。
- 暂停确认后，不再开始该 binding 的新原生输入提交或出站转发；来信可以继续持久入账，新增本地提交可排队并明确显示暂停。
- 所有可绕过 worker 的直接发送/flush 路径也须遵守所选 binding 的暂停策略；不能只停止一个后台循环就宣称已暂停投递。
- 已经在途的操作不宣称撤销。暂停结果区分已停止新增工作、仍有在途、结果待核对，不能以强杀伪造已完成。
- 恢复前核对服务/session/cwd、room pins、锁及 pending；保持同一身份时只启动一个所属 worker。身份改变则进入重新绑定流程。
- detach 保留现有“停用绑定”的含义。建议的 bridge pause/resume 等入口只是设计候选，不能混淆现有 bridge start 和 detach。

### 4.3 不确定状态分层处理

| 状态 | 恢复原则 | 不允许的做法 |
|---|---|---|
| 跨节点 m_UUID 待确认 | 使用现有 node flush 对原 ID、原 payload 对账；匹配既有远端 event | 生成新消息 ID 代替重试 |
| q_UUID / outgoingPending | 先核对 q → 正式 event → m_UUID 来源；必要时补足持久关联设计，再提供可执行恢复 | 按正文相同猜关联、清 pending 后再造一次发送 |
| 原生 pending | 使用该 adapter 可提供的稳定 input ID、持久消息和完整内容证据 | 只看到 HTTP 成功就重置，或未知时重复 POST |
| ZCode 工具可读取/已读取 | 保持工具收件语义，查询原 MCP scope 与账本 | 伪造 native input ID 或套用原生 admission 恢复 |
| 残留 worker 锁 | 展示完整 owner/token/绑定与存活核验；仅在旧 owner 确定退出后，按审计计划处理 | 按 PID 数字或进程名批量杀进程、按文件年龄破锁 |
| 原生服务身份变化 | 停止旧绑定投递，重新选择准确服务、聊天及新 pins/scope | 因 session 字符串或标题相同自动沿用旧绑定 |

无法证明的结果以 needs-review/uncertain 等准确状态停留，是允许的终态；报告应说明已知证据、缺什么证据和下一步。首版不承诺自动修复所有 unknown。

### 4.4 升级和回退

先暂停并确认所属写入者，再离线备份、安装固定候选包、只读预检、显式恢复。检查旧节点身份、消息历史、绑定和 room；v0.2 的本机 room 不自动变成跨节点 room，Windows embedded 与 hcom 目录不互换。

回退必须使用经验证兼容的版本/格式，或旧二进制与其升级前备份。不得让旧程序直接写不兼容的新状态。升级后新增的消息不能被静默覆盖或自动重放；无法无损回退时明确停止并导出差异。两份复制 state 不得同时充当活动节点。

## 7. 真实项目试用方案

首选 Mac ZCode 3.14.3 桌面与 VPS OpenCode：同时补上 ZCode 跨物理机证据与项目交付闭环。原聊天保留各自上下文、模型和审批。ZCode 由操作者在同一聊天明确触发 inbox；autoWake=false 为符合设计的结果。

项目优先选择 agent-dialogue 自身的一项小型真实问题，例如统一诊断说明或兼容性缺口。由一端提出约束与验收，另一端提交文件或代码变更，前者独立检查后提出一次修订。具体问题在 ST-01 缺口清单形成后锁定，不预先写好对端答案。若用户指定实际项目和聊天则使用明确选择；未指定时仅建立本项目拥有的正常开发聊天，不猜最近窗口或借用未授权的正式聊天。

- 产物为可审阅的 diff、测试结果或文档修订，以 Git commit/路径/hash 关联；文件取得复用既有 Git/SSH，不新增文件传输协议。
- 最多 4–6 条正式业务消息，最多一次针对反馈的修订；到限或出现异常先停，回执不引发确认循环。
- 分两次短工作时段，中间空闲建议 30–60 分钟，再从原聊天继续；空闲期间不让模型轮询。不是 24 小时无人值守或长期可用性承诺。
- 第三位 Windows/其他端 reviewer 可扩展，不以所有 harness 两两组合通过作为首版门槛；若增加协调场景，仍由项目约定角色。
- 执行前复查网络、目标服务和模型可用性。OpenCode 新测试聊天选显式启用且目录显示零价格的模型；ZCode 保留原模型，不声称整条链免费。其他原生组合不重复正向问答，除非其运行合同改变。
- 每次恢复保留原 message/request/input 身份；失败另开结果版本，不为失败的未知消息换新 ID。
- 结束精确停止本轮 worker/转发，保留原生聊天和必要只读历史；不干预其他项目的进程、账号、审批或模型配置。

若 ZCode或远端不可达，先完成无模型阶段；真实跨机用例保持待执行。可在记录替代原因后使用既有验证过的不同 harness 路径，但不能将替代路径写成 ZCode 跨机通过。
