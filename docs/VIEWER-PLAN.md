# Agent 对话查看器 v1：任务规划

状态：COMPLETE（本地首版VIEW-01～10）。2026-10-18 用户要求先规划任务并说明意图；本轮只形成计划与记录，不实现页面、不启动新模型实验、不部署 VPS。既有 V0.3-DESIGN.md 执行项和历史验证结果保持原样。

## 1. 要解决的问题与首版交付

打开一个本地页面，选择项目 room 后，能够回答：哪些 agent 在交流、原文是什么、哪条消息回复了哪条问题、实际交入哪个原生会话、目前有哪些投递证据和缺失数据。

首版读取当前通信空间，或由操作者明确列出的多个本机 state。提供 room 列表、参与者身份、消息时间线、回复跳转、证据详情、实时更新和所选范围导出。新增查看命令与页面均为拟议接口，目前尚不存在。

默认只监听 127.0.0.1 的随机可用端口；不需要 VPS。消息正文继续以已有 hcom 账本为权威。查看器的索引可以丢弃重建，不成为发送、接收或恢复所依赖的状态。

## 2. 范围

| 首版包含 | 后续单独处理 |
|---|---|
| agent-dialogue 中实际交换的消息与投递证据 | 原 harness 的全部聊天、工具记录和未发到 room 的本地总结 |
| 一个或多个显式配置的本机通信目录 | 自动扫描用户 home、自动发现所有聊天 |
| 本地消息、本地 queued submission、跨节点消息的关联 | 自动控制进程、发送消息、重试、破锁、修改权限或成员 |
| 只读浏览、过滤、回复定位与导出 | 任意活跃桌面窗口接入 |
| 按来源显示数据完整性与最后更新时间 | 当前 Codex 内部 sub-agent 工具对话自动接入 |
| 为未来远端 reader 保留接口 | VPS、公网服务、账户体系与中心消息中继 |

本机多个 source 能用于观察两个独立节点的现有测试数据；真实双机通信和远端观察分别验收。网页不需要成为通信必经路径，关闭网页不影响 agent 通信。

## 3. 页面与使用流程

1. 用拟新增的 `agent-dialogue view` 查看当前空间；其他本机 source 由 CLI 明确登记。端口、主题等采用默认值，无需用户先决定。
2. 左侧列出 room：名称、完整 ID 的短显示、参与者、最近活动及需关注的状态。相同名称不合并。
3. 中间显示实际消息：发送者、接收者、node、harness、时间和正文；点击回复引用定位原问题。
4. 右侧展开身份与投递证据：node/binding/revision/session、来源账本事件、queued/forwarded/stored/admitted 记录、最后采集时间。
5. 多来源副本归为同一条逻辑消息，保留每一份证据。未关联到正式消息的 queued 请求单独标明。
6. 支持按成员、来源和状态筛选；搜索与导出明确标注选定 room 和数据范围。首版以文本阅读为主，不执行消息内 HTML，也不自动加载外部图片。

页面不提供发送、重试、启动 bridge 或恢复 pending 的按钮。原生会话 ID 可以查看和复制；未验证的桌面 deep link 不作为首版承诺。

## 4. 数据来源与只读边界

| 来源 | 读取内容 | 注意事项 |
|---|---|---|
| hcom 消息账本 | 正文、原始事件、本地回复、本地 submission、wire envelope | 核实 pinned hcom 的读取命令是否有初始化/迁移副作用 |
| dialogue/store.json | bindings、room、peer 公钥描述、inbox/outbox 映射 | `readStore` 不写文件，但缺失目录不能伪装成正常空空间 |
| 各 binding 的 worker.json | receipts、pending、outgoingPending、worker 状态 | 回执可能晚于消息更新，不能只监听新 event ID |
| 显式 source 配置 | source 名称、路径与采集范围 | 由操作者登记，不接受网页请求提供任意文件路径 |

不得调用 `loadOrCreateNode`、`withStore`、`listen`、`start`、`flush` 或 native resume 来读取状态；不得改变业务账本、绑定、发送/已读游标、pending 或进程生命周期。已 detach 的 binding 仍是历史身份，不能据此把过去消息改判为投递失败。

浏览器不得提供任意SQL；查询只能由reader使用固定模板或参数绑定构造。node.json仅提取public字段，worker runtime仅提取显示所需字段，worker token与完整SSH transport配置也不输出。

VIEW-01 必须先验证 `hcom events` 在空目录、既有目录和活跃 WAL 场景中的行为。若它会初始化、迁移或修改配置，则改用经过验证的 SQLite 只读 reader，拒绝不存在或不支持的 schema。不得用 immutable=1 假设活跃 WAL 不会变化。具体 reader 选择在此任务结束后记录理由。

API 仅输出字段白名单；节点私钥、原生服务密码、SSH 凭据不进入页面或导出。浏览器仅能访问 CLI 已登记的 source。默认无公网监听和跨域读取权限；本地访问会话与 Host/Origin 校验在服务层设计中一并完成。

## 5. 消息关联契约

| 对象 | 关联原则 |
|---|---|
| 本地事件 | 以 source identity + local event ID 定位，不能只使用数字 ID |
| 新 room | 使用 room ID、revision、manifest hash 区分；同名不等于同一 room |
| 旧版未 sealed room | 保留 source 范围，不猜测跨 source 共享身份 |
| 跨节点消息 | 以原始发送节点 + m_UUID 找候选，再比较规范 payload hash、room 与成员 pins；不一致标冲突，不覆盖 |
| q_UUID 请求 | 使用该 source 的 worker forwarded receipt，把 queue event 对应到正式 event ID/m_UUID；不靠相同正文合并 |
| 本地回复 | 解析同一 source 的数字 replyTo |
| 跨节点回复 | 解析 replyToMessageId，并验证原始参与者与 room；父消息缺失时显示未采集/未加载 |

跨节点副本与 q 请求折叠后仍可展开原始记录。正文相同、时间相近或别名相同都不能单独作为合并依据。跨机器时间仅辅助排序，来源内按事件序列保序；显式回复关系优先表达因果，不能宣称全局时钟严格同步。

同一个q_UUID若出现在多个本地event中，应标记异常并保留各事件，不能仅按q_UUID折叠；当前通信worker对提交事件的处理身份是本地event ID。

建议的纯投影层：`read source → normalize events → link queue/result → merge matching wire copies → link replies → attach evidence → build room view`。异常记录保留来源与原因，不让一条坏记录阻断全部 room。

## 6. 证据语义

| 展示 | 必须有的依据 | 不能推导的结论 |
|---|---|---|
| 本地排队 | 实际 submission 账本事件 | 对端收到 |
| 后台已转发 | source worker 的 forwarded 与正式消息映射 | 模型已经处理 |
| 对端已收妥 | outbox remote-stored 控制记录，或对端 inbox/账本证据 | 浏览器已经独立重验对端回执签名 |
| 原生已受理 | 接收端 native-admitted/admitted 回执与稳定 input ID | 原生 turn 已启动、模型任务已完成 |
| 已有关联回复 | 实际反向参与者消息及明确 reply 引用 | 项目任务全部完成 |
| 未知/暂停 | pending、unknown 或 worker error 等具体记录 | 发送一定失败或可以安全重发 |
| 未采集/来源过期 | 来源未登记、读取失败、旧快照或证据范围不足 | 对方离线、消息未发生 |

现有 outbox 不保存签名回执本体，只有 bridge 验证后的结果。首版如实注明证据来源，不为显示审计徽章而改动原协议。worker 也没有完整保存所有模型执行阶段，页面不虚构运行中、已读或完成状态。

状态是可并存的证据集合。一次重试失败不能抹去之前的已收妥证据；晚到回执需要更新已有消息，而不是复制一条对话。

## 8. 刷新、容量与错误处理

首版优先使用 Node 内置 HTTP、普通 HTML/CSS/JS 与单向事件流，保持现有轻依赖分发方式；具体 reader 依 VIEW-01 结论确定。先不引入新的权威数据库。

每个 source 维护独立读取进度，增量事件采用有界分页；状态文件变化另行追踪。viewer 自身的事件序列用于浏览器断线续读，不能借用 hcom listen 的已读游标。DB/source 被替换、游标越界或服务器重启时显式重同步。

历史分页目标为每页100条。以合成1万条逻辑消息、两个 source 为基准，目标首屏3秒内、新事件/回执通常2秒内可见；这些是待测验收目标，不是现有性能结论。来源不可读时保留已有画面并标记最后刷新时间。

## 9. 验收矩阵

| 场景 | 必须看到的结果 |
|---|---|
| 本地 A 问 B、B 明确回复 | 两条正式消息，回复能回到正确原问题 |
| q 请求被转发为正式消息 | 一条主消息及可展开提交证据，不计作两次 agent 发言 |
| 两个 source 都含 event 42 | 不串消息、不串回复 |
| 跨节点发送与接收副本 | 同内容显示一条消息，双方证据可展开 |
| 同候选ID但hash/room/pins冲突 | 明确冲突，不静默合并 |
| 回执晚于账本、重复/乱序采集 | 更新原消息，保留已有确认，无重复计数 |
| 原问题未加载/未采集 | 显示悬空引用及来源范围，不猜正文 |
| detach后查看旧对话 | 历史仍可读，身份不被新 alias 替代 |
| 来源不存在/权限拒绝/坏JSON/旧schema | 局部明确提示，其他source可继续看，不初始化源目录 |
| 页面重连、DB更换、后台通信继续 | 正确续读或重同步；通信行为和原生输入数不受查看器影响 |
| 正文含HTML/脚本/外部图片/类似命令文本 | 按不可信文本显示，不执行或自动联网 |
| 原生API、私钥、密码存在于state附近 | API/页面/导出无这些非白名单字段；任意路径读取被拒绝 |

首轮可复用既有 owned 测试场景的本机数据及脱敏合成 fixtures。证明实时变化时可先回放受控新增事件；需要真实模型重跑则沿用已授权的独立测试聊天和免费模型目录检查，保持原模型/权限，结束后清理测试 bridge。不得把回放写成新模型真实验证。
